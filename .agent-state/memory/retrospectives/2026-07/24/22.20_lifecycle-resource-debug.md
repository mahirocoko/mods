# Session Retrospective

**Session Date:** 2026-07-24
**Time:** 21:14–22:20 GMT+7
**Focus:** Diagnose CPU/RAM pressure and harden the Mahiro Herdr Lifecycle mod against persistent process polling
**Type:** Performance bug fix / runtime verification

## Session Summary
We confirmed that the new lifecycle adapter’s unconditional `ps` process-table scan was a real multiplied CPU cost across open Herdr panes. The final design does not rely on a root turn being terminal: tool boundaries create a bounded 10-second discovery window, and known background children retain scanning until a successful scan proves they ended. The source was installed locally; runtime verification after an Esc interruption found zero `ps` children sampled from the affected Letta host across 10 seconds.

## Key Code Changes
- Removed root-turn and active-tool state as an unbounded process-scan trigger.
- Use a bounded discovery deadline at recognized tool start/end boundaries.
- Keep scanning only while that deadline is live or a known child remains active.
- Retain known children through transient `ps` failures until a successful scan observes their absence.
- Bind events and async scans to a generation/scope so stale opens, closes, tool events, and completed scans cannot mutate a newer conversation.
- Suppress late tool-end discovery renewal after an observed interrupt and require a matching active tool before extending a normal discovery window.

## Architecture Decisions
The mod remains read-only and public-API-only. We did not infer a user interrupt from terminal text or process state, because the current Letta public mod events did not expose a terminal Esc event in the observed path. Instead, process polling is resource-safe even if root activity remains visually stuck. Herdr’s working label may therefore remain stale after Esc; claiming otherwise would be false.

## AI Diary
This session was a useful correction to my instinct to solve a state problem by adding more state detection. The first finding was straightforward: polling the global process table once a second in every open pane was unnecessary and visible in the machine profile. The difficult part was not writing a shorter condition; it was refusing attractive but unproven interpretations of `aborted`, `cancelled`, and terminal-looking UI copy. Every verifier pass found a different path where an apparently reasonable shortcut could leak work into another conversation, restart a polling window, or silently lose a background child. That was frustrating because it lengthened a small performance fix, but it was the right friction. The live Esc trace made the boundary clear: this host does not offer a public terminal interrupt event to the mod. From there, the honest target changed from “make Herdr know Esc happened” to “ensure lack of that event cannot keep expensive polling alive.” The final PID-level sample is much stronger evidence than a green unit test alone. I should have started with that contract distinction sooner.

## Honest Feedback
1. I initially treated generic aborted/cancelled reasons as proof of human intent. The verifier correctly rejected that; terminal reason and actor are different facts.
2. I allowed the first adaptive gate to depend on root turn/tool maps that themselves can remain stale when the host does not emit terminal events. This recreated the very failure mode we were removing.
3. The implementation-review loop became too serial and patchy. The durable lesson is to model conversation generation, event correlation, and async callback ownership before changing polling cadence, rather than bolt them on after each counterexample.

## Lessons Learned
- A bounded poller needs independent ownership and expiry; it cannot inherit liveness from event state that may never terminate.
- Preserve a known child through failed observations. Only a successful observation may prove it ended.
- Public event absence is a product constraint, not a reason to simulate certainty through terminal parsing or guessed stop reasons.
- A real PID-level before/after probe is required for a performance claim.

## Next Steps
