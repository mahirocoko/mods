## AI Diary

I began this work with a protective policy that was too willing to treat a
sensitive-looking word as evidence of a sensitive read. Mahiro's challenge was
useful because it exposed a distinction I needed to apply while writing, not
only explain afterward: a filename in a pattern or a comment does not have the
same role as a target operand. I also saw how quickly a green synthetic suite
can reward the implementation's assumptions. The first writer's tests passed,
yet a few deliberately contrasting shell shapes disproved readiness. I had to
retain that contradiction rather than convert the green count into confidence.

The most instructive runtime moment was the metadata command transformed by
RTK. Source tests for the raw command were not enough; the final carrier had its
own semantic boundary. I corrected the exact projections instead of widening
RTK permission globally. Later, the PyPI dictionary defect reminded me that
filtered output is still real runtime code. Hiding passwords does not excuse
unsafe ownership of user-selected object keys. A small Map repair was more
grounded than another string blacklist.

I am satisfied with the live results, but not with every part of my process.
Repeated initialization and verification added time, and some reviewer prose
claimed more than its runner established. I challenged the actual artifacts,
recorded unsupported claims, and stopped once matching proof existed. The final
state is deliberately modest: useful filtered access, fewer demonstrated false
positives, retained protection and named limits. I should preserve that honesty
when describing the release rather than advertise that the guard never blocks
incorrectly again.

## Honest Feedback

Three friction points deserve explicit attention. First, parser work expanded
into a substantial single-file change. The implementation remained owner-local,
but future work should begin with exact role and runtime-carrier counterexamples
before adding another parsing branch. Second, writer and reviewer reports both
contained unsupported details: payload fields, confinement, native read APIs,
minimal subprocess environments or compatibility claims did not always match
the code. Main's raw-artifact audit was necessary, and a report-ready callback
was never sufficient acceptance evidence. Third, workflow overhead was visible.
Several fresh sessions were justified by concrete refutations, but initialization
and repeated broad checks still cost time. A future narrow follow-up should
reuse established evidence, rerun only affected checks, and reserve another
specialist for an actual unresolved boundary. These are process critiques, not
reasons to weaken independent security verification or pretend remaining limits
have disappeared.

## Lessons Learned

- Input roles and final transformed arguments own classification, not word
  presence alone. The existing tool-transform-order reference already captures
  this transferable decision; no duplicate learning is promoted here.
- Mixed credential/configuration files need explicit format-specific filtered
  capabilities, not blanket raw-read permissions or a universal key-name filter.
- User-selected dictionary names need own-key ownership; filtering values does
  not prevent prototype mutation.
- Reported compatibility and security claims must match actual source, runner
  arguments and performed tests. Finite assertions are not universal guarantees.
- Human acceptance, source proof, installed parity and loaded live behavior are
  distinct gates. A package copy alone does not establish a successful reload.
